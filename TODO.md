## Current status and short-term goal

secretops is a CLI-first SecretOps broker. It is not a vault: external vaults remain the source of truth, and agents operate on names, metadata, plans, approvals, and safe results rather than secret values.

The Infisical adapter hardening is implemented and verified against the NAS instance. The dedicated local SSH broker separates agent access from vault credentials and human approval.

**Short-term goal:** first use (section 7), on a test repository first and then in a real project: use the published release for a real project and record where it is hard.

The previous goal is reached: a human enters an externally created API key through a hidden prompt, the broker stores it in Infisical, and an agent transfers it to GitHub through a separately approved plan, documented and repeatable from a clean installation.

### 9. Plan lifecycle and audit hardening — from the 2026-11-14 code review

Found by reading the code; none is reproduced with a test yet. The execution lock comes before the first real-project use (section 7); the rest follows it. Changes to security behaviour go through a branch and review, each with a short contract and tests.

- [x] Close the race between `approve-plan`/`reject-plan` and `execute-plan`. This is the next code change, before the rest of this section: a late `approve-plan` that loaded `planned` can write `approved` over `executed`, after which the plan can be executed a second time (confirmed in the code on 2026-11-14 and stated in `SECURITY_MODEL`). `approve-plan` and `reject-plan` take no lock for ordinary plans and write the status from the copy they loaded, so a decision made at the same moment as an `execute-plan` on a still unapproved plan can be lost to the `failed` status that `execute-plan` writes, or can replace it. No unapproved provider call results. Take the plan lock in both commands and read the plan again under it, as `execute-plan` does; decide together with the item below on what `execute-plan` does to a plan that still waits for approval. In the same change, give a clean refusal when the lock file cannot be opened: `secretops add` (on submission) and rejection of a human-entry plan catch only the busy case, so `PlanLockError` ends in a traceback there. `execute-plan` already prints `FAIL plan lock could not be taken`; no value is shown in that traceback, and the behaviour predates the execution lock.
- [x] Hold the plan lock during `execute-plan`. Today only `secretops add` and the rejection of a human-entry plan take `plan_lock`, so two `execute-plan` calls started at the same time can both read `approved` and both run, for example a double rotation. "A plan runs only once" must also hold for concurrent calls: the second call stops with the existing "plan is in use" message and makes no provider call.
- [x] Vault paths (generate, rotate, import, copy): when the plan status cannot be saved after a confirmed write, `execute-plan` ends in a traceback, while the GitHub path prints "do not run this plan again". Give the vault paths the same message and exit code. Found in the review of the decision lock.
- [x] Write an audit event for `approve-plan` and `reject-plan`, with the plan id and, on approval, the approval digest. Today the decision is visible only in the plan file.
- [x] Refuse `details` keys in `write_audit_event` that would replace a core field (`timestamp`, `action`, `secret_name`, `env`, `status`, `secret_value_logged`, `plan_id`).
- [x] Decide whether approval expires. Decided: yes. Plans record `planned_at` (digested) and `approved_at` (UTC); `execute-plan` refuses an approval older than `approval_valid_hours` in the policy (1 to 168, default 24), an approval time in the future, and an approved plan without an approval time (approved by an older version), before any provider call, and marks the plan `failed`: the way on is a new plan and approval, no re-approval. `contract_version` stays 1 (optional fields; older planned plans keep working). `secretops add` records the time; no expiry applies there.
- [x] Decide what `execute-plan` does to a plan that still waits for approval. Decided: refuse with exit 1 and no provider call, write a `failure` audit event with `failure: approval_pending`, and leave the plan `planned`, as the human-entry path does; the human can still approve it. On every execute path (generic policy check and the per-action checks of generate, rotate, copy, GitHub write and sync). Unchanged: `rejected` and `executed` are refused as before; a `failed` plan that needs approval is refused and stays `failed` (superseded 2026-11-22: every `failed` plan is final, see below); a plan the environment policy refuses is marked `failed`, since approval cannot make it run.

The packaged default lists `prod` next to `production` for the metadata checks, so they work in both; writes are refused in both.

## Safety invariants

- Never print or log secret values, place them in plans/audit, or pass them in command-line arguments. Plans and preflight do not generate values or mutate secrets.
- Use stdin or narrowly controlled provider input; provider-required temporary files are restricted and broker-private.
- Treat provider errors as errors, not missing secrets. Report unconfirmed writes honestly; never automatically retry or roll back partial writes.
- Generate is create-only by default; rotate explicitly replaces an existing vault secret. Infisical currently checks then writes without an atomic create-only guarantee.
- Rotation and target sync remain separately authorized operations. GitHub metadata verification does not read secret values.
- Agents must not read `.env`, tokens, keys, machine identity secrets, or private credential files, nor invoke provider commands to print/list/dump/export secrets. Follow `AGENTS.md` and broker command restrictions.
